# Real-time report and message updates

The web uses authenticated `GET /api/notifications` snapshots and `GET /api/notifications/stream` invalidations. The server subscribes to Supabase with its private service credentials. Only table invalidations cross the stream; records are fetched through authenticated APIs. Browser writes invalidate affected screens immediately, while focus/reconnect and the existing 10-second checks reconcile missed events.

The mobile app shares one authenticated long poll at `GET /api/mobile/changes?cursor=...` through `LiveDataProvider`. A database event ends the pending request immediately. The response contains a cursor, changed table names and connection status, never row contents or service credentials. The client starts the next poll automatically. The server keeps a bounded event history to cover events between polls, reconciles after a subscription reconnect or instance restart, and releases idle subscriptions. Multiple API instances can require a full reconciliation when their cursors differ.

The mobile connection pauses in the background and resumes with a fresh snapshot. Failed connections retry automatically. A 15-second foreground reconciliation also covers missed replication events and unavailable subscriptions. Home, My Reports, browse results, report categories/locations, recovery feedback and messages update automatically. Only focused screens reload their records; the shared message badge stays current throughout an authenticated session. Background updates preserve message and report drafts, chosen filters and valid locations. Removed locations are cleared and submission still rechecks approval. Routine refresh buttons and pull-to-refresh controls have been removed; failure-only Retry controls remain.

`MessageBadgeProvider` owns the mobile conversation/message snapshot. Message access is scoped to the signed-in account by the API, including safe support for legacy conversation names. The Messages screen acknowledges incoming admin messages only while focused, foregrounded and successfully loaded. Web counts incoming user messages and acknowledges only the opened conversation. Outgoing messages never create an unread badge. Read receipts persist per account on the current device; they do not synchronize between devices. Web report receipts are recorded only after the administrator opens report details.

`server/enable-realtime-notifications.sql` enables publication for reports, matches, activity, messages, conversations, categories, users, locations, recoveries and feedback. It is repeatable, preserves existing publication members, skips missing optional tables and does not change rows, grants or RLS policies. On 2026-11-03 it was applied to the connected project as `enable_mobile_and_admin_live_data`; all eleven tables were confirmed published, with private-table RLS still enabled. The local mobile endpoint returned 401 without a session and 200 with `realtime: true` after the real Supabase handshake. No real report or message was created for verification.

Both Express entry points mount the mobile changes route. The local API was restarted. Hosted environments require the updated API deployment, and mobile users need the updated JavaScript/app build. No new dependencies, environment variables or client secrets are required.

The mobile report forms and Messages now use measured window coordinates to reserve only the keyboard overlap left after native resizing. This avoids applying Android resize and a fixed keyboard offset twice. Report inputs register their actual native refs, reveal the focused field after keyboard/layout changes, and scroll long text internally. The floating tab bar and global speech stop overlay stay clear while typing. Automated Android/iOS branch tests cover resized and overlay keyboards, safe-area coordinates, scroll geometry and draft retention. Native emulator testing on this machine was blocked when Expo Go installation hit `ENOSPC`; no native layout pass is claimed. Reload the development app on a phone and verify both report text fields and a long message before release.

The security advisor reported only informational [RLS enabled without policies](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy) notices on private tables. These tables deliberately deny direct client access and are served through authorized server routes; publication did not add client read policies.
